**Legend: the honesty convention**, copied from the
[model README](likec4/README.md#the-honesty-convention).

The model shows what the code on `main` actually does, and marks everything else.
Every element and relationship that is not plainly live says so.

Element tags (defined in `spec.c4`, styled in `views.c4`):

| Tag         | Use it when                                                                            |
| ----------- | -------------------------------------------------------------------------------------- |
| `#live`     | It is on `main` and runs in the deployed environment today.                            |
| `#scaffold` | Code exists on `main` but is a stub or is not wired up, so it does not do the job yet. |
| `#notBuilt` | Nothing on `main`, and no decision to build it yet. Drawn faded.                       |
| `#decided`  | The owner has decided to build it, but it is not on `main` yet.                        |
| `#retiring` | It is on `main` today and has been decided for removal.                                |

Relationship kinds (`a -[kind]-> b`; a plain `->` means "live today"):

| Kind       | Use it when                                                                |
| ---------- | -------------------------------------------------------------------------- |
| `planned`  | The connection is not built, and there is no decision to build it yet.     |
| `decided`  | The connection is decided and will be built, but is not on `main` yet.     |
| `retiring` | The connection exists in the code today and is going to be removed.        |
| `event`    | An asynchronous message (queue, event stream, IoT Hub route) that is live. |

**The rule:** a view that shows current state never draws a decided or not-built
path as if it were live. Decided designs go in their own views, whose id ends in
`Target` (for example `probeAlertTarget` in "Add a flow" below). A current-state view
may still include a `#decided` or `#notBuilt` element, because the view styles
render those dashed or faded, but its flows describe only what runs today.

## Functions API

Every route is anonymous at the Functions runtime on purpose: Easy Auth (default-deny,
Return401) has already validated the token. The cook, device and temperature routes first
call `getDeviceOwnership`, one point read on `devices`. For a device the caller does not
own: cooks start/stop answer `403 DEVICE_NOT_OWNED` (no write, no event), `GET`/`PATCH
/devices/{id}` answer 404, `DELETE /devices/{id}` answers `403 DEVICE_NOT_OWNED` (nothing
deleted) and `404 DEVICE_NOT_FOUND` for an unknown device, and temperatures current/history
answer `404 DEVICE_NOT_FOUND`.

## Cosmos DB

Seven containers in one shared-throughput database (400 RU/s), their partition keys, and
who touches each: `devices /id`, `temperatures /deviceId`, `cooks /userId`, `users /id`,
`recipes /userId`, `temperature-rollups /deviceId` and `leases /id`. The ownership check
`getDeviceOwnership` is one point read on `devices`. IoT Hub's `cosmos-storage-route` is
the only writer of `temperatures`, with the partition value taken from `{deviceid}`; its
device-side writers are the Pi data-pusher and the dev simulated device.
`rollupTemperatures` reads its change feed (checkpoints in `leases`) and is the only
writer of `temperature-rollups`, which the cook chart reads.

## Delivery pipeline

Pull requests feed two workflows. CI/CD Pipeline runs on every pull request and push to
main: lint and test, the Cosmos emulator tests on `windows-2025`, builds, Terraform
validation, the security scan, the `no-real-time` guard and `web-e2e`. Test repeat
(`test-repeat.yml`) runs on pull requests only: each affected non-live suite 50 times in a
row, its emulator suite on `windows-2025`; it starts nothing and is not a required check.
A green CI run on main starts the apply, then the deploy and its two acceptance jobs. When
a web-acceptance sign-in step fails, the proof writes a scrubbed `sign-in-diagnostic.txt`,

Steps:

- **1.** cooks (`meatgeek.web.cooks`) → cooks (`meatgeek.cloud.api.cooks`): POST /cooks. Through Easy Auth and the principal (`userId = tid:oid`; a missing header is 401). The web app's start form sends a client-generated id, one per intent, so a retried submit starts the cook once. The ownership check is one point read on `devices`: a foreign or unregistered device gets 403 `DEVICE_NOT_OWNED`, with no write and no event. The live callers are the web app and the acceptance proofs.
- **2.** cooks (`meatgeek.cloud.api.cooks`) → cooks (`meatgeek.cloud.data.cooks`): cook and device lock. One transactional batch in the caller partition: the cook and its device lock commit together, so a device holds at most one active cook (MG-84).
- **3.** cooks (`meatgeek.cloud.api.cooks`) → IoT Hub: set desired: activeCookId, correlationId. After the write, synced to the device lock under the twin etag (`If-Match`): GET the twin, read the active cook from Cosmos, PATCH only if they differ, then re-read. Managed identity with `IoT Hub Twin Contributor`. A failed sync answers 503 `DEVICE_TWIN_UPDATE_FAILED`; the cook stays written and a retry of the same request heals the twin.
- **4.** IoT Hub → twin client: desired properties. Delivered on connect (a full GET) or on change (a patch), so an offline Pi catches up. Patches apply in `$version` order.
- **5.** twin client → cooksession: persist cook, correlation id, version. Written to `/var/lib/meatgeek-pusher/cooksession.json`. From then every reading carries this cook id and correlation id. (Opens `telemetry`.)
- **6.** twin client → IoT Hub: reported: applied. `activeCookId`, `correlationId` and `appliedDesiredVersion`: the acknowledgement. Proven live by the `device twin` acceptance proof, with the device offline when the cook starts.
- **7.** cooks (`meatgeek.cloud.api.cooks`) → SignalR Service: cook_started to the owning userId. Sent only after the write succeeds, on hub `temperatureHub`, to the caller's `userId` ("<tid>:<oid>"), never to the deviceId (MG-30). The envelope carries `correlation: CorrelationContext { id }`, the same id the twin carries. The `signalr isolation` proof receives it as the owner. The web live panel listens for `temperature` and `cook_stopped`: when the cook is stopped, `cook_stopped` reaches it the same way and the page shows the cook as ended.

## Flow: live telemetry proof (dev acceptance)

Every Deploy Dev App acceptance job proves the telemetry path end to end:
`telemetry-roundtrip.proof.ts`, then `telemetry-volume.proof.ts`. `simdevice` sends as
`meatgeek-dev-simulated-smoker` (MQTT 8883, device SAS, QoS 1, the data-pusher's own
publish code); no Function is in the write path.

Measured (single dev samples, not targets): `roundtrip-ms` 1211 (run 44603121177) and
1235 (run 44612029684); `topup-sent`/`topup-ms` 2175 / 109996 (~19.8 readings/s, run
44612029684). Before HAR-75 history paged by `OFFSET` and every request paid a `COUNT(1)`:
in run 44612029684 the 100-reading page cost 11.95 RU at offset 0 and 24.12 RU at offset
8600. Since HAR-75 it pages by continuation token with no COUNT, and the volume proof fails
unless the last page of a walk costs at most 1.5 x the first.
