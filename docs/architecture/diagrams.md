The interactive site, https://stevebargelt.github.io/meatgeekv2/, is the primary way to read the architecture:
it draws every view with its styles, shows each element and step with its description,
and links each view to the views below it. This file renders the same views as Mermaid
so that they also show inline on GitHub. Mermaid keeps the fill colours but not the faded
opacity or the dashed and dotted borders the site gives to elements that are not live,
so check the site when an element's state matters. A flow (a dynamic view) is drawn as a
flowchart without step numbers; its numbered steps and their notes follow the diagram.

16 views, grouped as: Landscape and containers (3), Drill-downs (6), Deployment (1), Flows, today (6).

**Legend: the honesty convention**, copied from the
[model README](likec4/README.md#the-honesty-convention).

The model shows what the code on `main` actually does, and marks everything else.
Every element and relationship that is not plainly live says so.

Element tags (defined in `spec.c4`, styled in `views.c4`):

| Tag         | Use it when                                                                            |
| ----------- | -------------------------------------------------------------------------------------- |
| `#live`     | It is on `main` and runs in the deployed environment today.                            |
| `#scaffold` | Code exists on `main` but is a stub or is not wired up, so it does not do the job yet. |
| `#notBuilt` | Nothing on `main`, and no decision to build it yet. Drawn faded.                       |
| `#decided`  | The owner has decided to build it, but it is not on `main` yet.                        |
| `#retiring` | It is on `main` today and has been decided for removal.                                |

Relationship kinds (`a -[kind]-> b`; a plain `->` means "live today"):

| Kind       | Use it when                                                                |
| ---------- | -------------------------------------------------------------------------- |
| `planned`  | The connection is not built, and there is no decision to build it yet.     |
| `decided`  | The connection is decided and will be built, but is not on `main` yet.     |
| `retiring` | The connection exists in the code today and is going to be removed.        |
| `event`    | An asynchronous message (queue, event stream, IoT Hub route) that is live. |

**The rule:** a view that shows current state never draws a decided or not-built
path as if it were live. Decided designs go in their own views, whose id ends in
`Target` (for example `probeAlertTarget` in "Add a flow" below). A current-state view
may still include a `#decided` or `#notBuilt` element, because the view styles
render those dashed or faded, but its flows describe only what runs today.

## Functions API

Every route is anonymous at the Functions runtime on purpose: Easy Auth (default-deny,
Return401) has already validated the token. The cook, device and temperature routes first
call `getDeviceOwnership`, one point read on `devices`. For a device the caller does not
own: cooks start/stop answer `403 DEVICE_NOT_OWNED` (no write, no event), `GET`/`PATCH
/devices/{id}` answer 404, and temperatures current/history answer `404 DEVICE_NOT_FOUND`.

each: `devices /id`, `temperatures /deviceId`, `cooks /userId`, `users /id`,

`devices`. IoT Hub's `cosmos-storage-route` is the only writer of `temperatures`, with
the partition value taken from `{deviceid}`; its device-side writers are the Pi
data-pusher and the dev simulated device.

- **9.** telemetry-volume.proof.ts → simdevice: simdevice --count N --inflight 32 --interval 50ms. Only if the walk counts fewer than 8,640 (12 h at one every 5 s). N = 8,640 - counted + 60. Measured `topup-sent`/`topup-ms` 2175 / 109996, ~19.8 readings/s.
- **10.** simdevice → IoT Hub: N readings, MQTT QoS 1
- **11.** IoT Hub → temperatures (`meatgeek.cloud.data.temperatures`): cosmos-storage-route
- **12.** telemetry-volume.proof.ts → temperatures (`meatgeek.cloud.api.temperatures`): GET /temperatures/current/{id}, until the top-up end. After a top-up only. Polled every 10 s, 15 min cap, until the current reading is at or after the reading 32 places from the top-up last.
- **13.** telemetry-volume.proof.ts → temperatures (`meatgeek.cloud.api.temperatures`): the same walk again. Prints `history-ru-first-page`, `history-ru-last-page` and `history-pages`; fails unless the last page costs at most 1.5 x the first.
- **14.** temperatures (`meatgeek.cloud.api.temperatures`) → temperatures (`meatgeek.cloud.data.temperatures`): one page per request: maxItemCount + continuation token. No COUNT and no OFFSET (HAR-75), so a deep page costs what the first does. The job copies every `METRIC` line into the run summary.
