# CI/CD Pipeline

MeatGeek V2 runs continuous integration through `.github/workflows/ci.yml`, and deploys through separate workflows. Dev **infrastructure** reconciles automatically through CI: `ci.yml`'s `validate-infrastructure` job validates every infrastructure change **credentiallessly** — it holds no Azure identity at all — and `.github/workflows/infra-apply-dev.yml` applies on merge to `main`. The dev **API** then deploys automatically too: `.github/workflows/app-deploy-dev.yml` publishes it to the dev Function App after each dev infra apply and runs the live acceptance suite against it. Production deployment is split into two standalone workflows — `.github/workflows/infra-deploy-prod.yml` and `.github/workflows/app-deploy-prod.yml`. Every merge to `main` also publishes the architecture site to GitHub Pages through `.github/workflows/architecture-site.yml`. This document describes the CI jobs that run, why the TypeScript build matrix is scoped the way it is, how the dev GitOps loop and the prod deploys work, the branch-protection rules on `main`, and the npm/lockfile constraint the runners depend on.

**Terminology used throughout, and in the tickets:** **MG-24** = _Terraform reconciliation_ (operator-run, from a workstation, against the persistent remote backend). **MG-23** = _automated dev GitOps reconciliation_ (CI-run, no operator apply for steady state).

## Triggers

The pipeline runs on:

- **push** to `main`
- **pull_request** targeting `main`

This repository is **trunk-based on `main`**. There is no `develop` branch and none will be created; `develop` was removed from the trigger lists under MG-23 as dead configuration.

Environment defaults used across jobs: Node.js `20`, Go `1.21`.

`ci.yml` carries exactly **one** infrastructure job, `validate-infrastructure`, and it runs on **every** pull request and every push — not only on PRs touching `apps/infrastructure/**`. The two earlier pull-request-only infrastructure jobs (`detect_infra_changes` and the PR-time plan job) are **both gone**: with no Azure identity to protect, there is nothing for a change-detection job to gate, and running the checks unconditionally means a change that breaks them cannot slip through by touching a file outside the path filter. It **is** a required status check — see [Branch Protection](#branch-protection).

### Why the TypeScript build matrix is `api` + `web` only

`build-typescript` compiles only the apps that NX builds with `@nx/js:tsc`/bundlers — `api` (Azure Functions) and `web` (React/Vite). `mobile` is a React Native app; it is not `tsc`-built in CI, so it is intentionally **absent** from the `build-typescript` matrix. `mobile` is still linted and tested (it appears in the `lint-and-test` matrix); it is simply not compiled here.

Adding a new buildable TypeScript app? Add it to the `build-typescript` matrix. A new React Native target does **not** belong there — keep it in `lint-and-test` only.

### Cosmos emulator tier (HAR-12)

`nx test api` runs the cooks persistence specs against hand-written fakes, so real Cosmos behaviour — `/userId` partitioning, `409` on a duplicate create, all-or-nothing transactional batches, `If-Match` replaces, single-partition `ORDER BY` paging with continuation tokens, and `requestCharge` — is never exercised by it. The emulator tier fills that gap for the cooks repository.

**What runs.** `apps/api/src/**/*.emulator.spec.ts`: today `cooks-repository.emulator.spec.ts`, `devices-repository.emulator.spec.ts` (HAR-20) and `temperatures-repository.emulator.spec.ts` (HAR-28) under `apps/api/src/shared/cosmos/`. The cooks spec is described here; the other two follow the same pattern. The temperatures spec seeds IoT-Hub-shaped documents modelled on `docs/infrastructure/evidence/mg73-observed-routed-document.json` and proves the newest-reading query and the MG-73 identity rule against the real query engine. It builds a throwaway database and a `cooks` container whose name and partition key path are read from `azurerm_cosmosdb_sql_container.cooks_shared` in `apps/infrastructure/modules/cosmos-db/main.tf`, reaches it through `CosmosAdapter`'s `clientFactory` seam, and runs the unmodified `CooksRepository` on the real `@azure/cosmos` SDK. Cases: start a cook and read it back; a retried start with the same id (MG-84) — sequential and concurrent — creates exactly one cook; a busy device refuses a second cook until the first is stopped; stop and read back stopped, idempotently; concurrent stops converge on one `endTime`; list-by-user returns only that user's cooks, newest first, in pages of 2; every operation reports a numeric `requestCharge` greater than 0. The database is deleted afterwards.

**Targets.** The tier has its own target, `npx nx run api:test-emulator` (`apps/api/jest.emulator.config.ts`, `cache: false`). The default `apps/api/jest.config.ts` ignores `*.emulator.spec.ts`, so `npx nx test api` stays green without an emulator. When no emulator is reachable the tier **fails** (non-zero exit, every case red with an "emulator unreachable" message); it never skips.

**Credentials.** The emulator's well-known account key is a public constant and appears only in the spec file. The deployed path is unchanged — `productionSeams` still builds a `ManagedIdentityCredential`, and no key or connection string exists in non-test code under `apps/api/src`.

**Which emulator, and why.** CI uses the **classic** Linux emulator (`mcr.microsoft.com/cosmosdb/linux/azure-cosmos-emulator`, pinned by digest in `ci.yml`), not the lighter `vnext-preview` image. `vnext-preview` was tried first and lacks two things `cooks-repository.ts` relies on:

- it ignores the page size on a single-partition `ORDER BY` query — `maxItemCount: 2` over five cooks returns all five in one page with no continuation token;
- it reports `requestCharge: 0` for every operation inside a transactional batch (the batch total is only in a response header), so a created start reports 0 RU.

The classic engine pages and charges like the service, and all cases pass against it. It serves HTTPS with a self-signed certificate; trust that certificate with `NODE_EXTRA_CA_CERTS` rather than disabling TLS.

**CI.** The `api-cosmos-emulator` job starts the emulator as a service container on port 8081, waits (bounded at 5 minutes) for the emulator's final `Started` log line and for its certificate to download, exports `NODE_EXTRA_CA_CERTS`, then runs `npx nx run api:test-emulator`. It runs on every pull request and every push to `main`.

**Run it locally (Docker).**

```bash
docker run -d --name cosmos-emulator -p 8081:8081 \
  -e AZURE_COSMOS_EMULATOR_PARTITION_COUNT=3 \
  mcr.microsoft.com/cosmosdb/linux/azure-cosmos-emulator:latest
# Wait for the final "Started" line (one to two minutes):
docker logs -f cosmos-emulator
curl -sk https://localhost:8081/_explorer/emulator.pem -o /tmp/cosmos-emulator.pem
NODE_EXTRA_CA_CERTS=/tmp/cosmos-emulator.pem npx nx run api:test-emulator
```

The classic image is `linux/amd64` only. On Apple Silicon add `--platform linux/amd64`; it runs under Docker Desktop's emulation (slower to start). Point the tier at a different endpoint with `COSMOS_EMULATOR_ENDPOINT` (default `https://localhost:8081`).

## Deployment

Deployment is **not** part of branch protection — it runs after a merge lands on `main`, so it can never be a merge gate.

### Dev infrastructure — automated GitOps reconciliation (MG-23)

Dev infrastructure reconciles **through CI**. That is the intended steady state: an infrastructure change is written in a PR, **validated credentiallessly** by CI, reviewed, merged, and applied by CI. Nobody runs an apply from a workstation to keep dev in sync.

The loop is two halves:

| Half                               | Where                                | Identity / Environment                          | What it does                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                |
| ---------------------------------- | ------------------------------------ | ----------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **PR validation (credentialless)** | `ci.yml` → `validate-infrastructure` | **no identity, no environment**                 | `assert-credentialless.sh` → `terraform fmt -check -recursive` → `terraform init -backend=false -input=false -lockfile=readonly` → `terraform validate` → `terraform test` (root) → `tf-static-checks.sh` → `bootstrap.test.sh` → destroy-guard fixtures → V1 Cosmos export tool tests (MG-48, `run-tests.mjs` against a fake client — no network, no credentials) → dev IoT device fixture tests (MG-67, `iot-fixture/run-tests.mjs` against an injected fake reader and fake spawn — no network, no credentials) → per-module `terraform test` (`modules/functions`, `modules/iot-hub`, `modules/monitoring`) → OTel config validate. **No `terraform plan`, no backend, no Azure login** |
| **Apply on merge**                 | `infra-apply-dev.yml` → `apply`      | infra-apply identity, `development-infra-apply` | plan → pre-apply secret gate → destructive-change circuit-breaker → apply **that saved plan** → post-apply state gate → final drift plan that **fails on drift**                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                            |

**PR validation (`validate-infrastructure`) is credentialless — that is the design, not an omission.** The job declares `permissions: contents: read` and nothing else: **no** `id-token: write`, so GitHub never injects the OIDC token-request pair; **no** `environment:`, so no federated credential can be selected; **no** `azure/login`; and no client id or subscription id anywhere in the file. An `env:` block additionally pins `ARM_USE_OIDC`, `ARM_USE_CLI`, `ARM_USE_MSI` and `ARM_USE_AKS_WORKLOAD_IDENTITY` to `'false'`, so the `azurerm` provider **refuses** ambient credentials even if a future edit or a self-hosted runner leaves some lying around. The first step, `scripts/assert-credentialless.sh`, proves at runtime what the declaration claims statically — it fails the job if any `ARM_*`/`AZURE_*` credential material, cached `az login`, or `ACTIONS_ID_TOKEN_REQUEST_URL`/`ACTIONS_ID_TOKEN_REQUEST_TOKEN` is present, and it also fails if it discovers zero test files, so it cannot certify an empty gate.

Everything after that runs against the checked-out tree alone. `terraform init` passes `-backend=false -input=false -lockfile=readonly`; **`-backend=false` is an `init` flag and is not accepted by `terraform validate` or `terraform test`** — it belongs on `init` alone, and it is exactly why this job needs no state credential: with no backend configured, nothing reaches `meatgeek-v2/dev.tfstate`. `terraform test` runs against **mock providers**, so it provisions nothing. Since **MG-39** the per-module inits pass `-lockfile=readonly` too, against each module's own committed lock: `modules/iot-hub` previously declared no `azurerm` constraint, so its init resolved **latest** and picked up the breaking azurerm v5.0.1 the day it shipped, reddening every PR with nothing in the repo having changed. `tf-static-checks.sh` **check 16** now fails any module that carries a `*.tftest.hcl` without both an explicit provider version constraint and a committed `.terraform.lock.hcl` — so adding module tests carries that obligation (see [Provider pinning & lock files](../../apps/infrastructure/README.md#provider-pinning--lock-files)). `tf-plan-secret-inspection.sh` and `tf-plan-destroy-guard.sh` are never pointed at a real plan before a merge — there is no plan to inspect. Both are exercised as **fixture regressions**, so what CI proves pre-merge is that each gate still fails closed on the crafted fixtures (under bash _and_ dash), not that a particular plan is clean. They are wired into **different jobs**, which is worth knowing if you go looking for them: the destroy-guard fixtures are a `validate-infrastructure` step (`run-destroy-guard-fixtures.sh`), while the secret-gate fixtures are driven from the `api-interfaces` leg of `lint-and-test`, whose Jest suite shells out to `run-flex-secret-gate-fixtures.sh`. Both jobs are required checks, so neither regression can be skipped — but only `infra-apply-dev.yml` ever runs either gate against a real plan or real state.

**What that costs, stated plainly:** a pull request no longer gets a remote-state plan, so a reviewer cannot see the concrete resource diff before merge. The authoritative plan is the one `infra-apply-dev.yml` takes **post-merge** against real state, under the apply identity, screened by the pre-apply secret gate and the destroy circuit-breaker, and proven convergent by the final drift plan. What it buys is that no pull-request-reachable job holds an Azure identity, so attacker-supplied PR code has no path to `tfstate-dev` or the live IoT Hub SAS keys in it. **Restoring a PR-time plan cannot be done without re-granting a PR-reachable identity read on live state** — that is a threat-model change, not a CI convenience change.

**Apply on merge (`infra-apply-dev.yml`).** It triggers on `workflow_run` after the **CI/CD Pipeline** completes, and only when `conclusion == 'success'`, `event == 'push'`, and `head_branch == 'main'` — all three, because `workflow_run` also fires for PR-triggered and fork CI runs. It checks out `workflow_run.head_sha` (the exact commit CI went green on, never a floating ref), applies the exact saved plan, and ends with a `-detailed-exitcode` plan that **fails the run on any drift**. A `workflow_dispatch` entry exists as a **branch-restricted recovery path only**; it runs the identical sequence with no shortcut and carries its own manual approval, which the automatic path deliberately does not.

**Stale trunk is never applied.** Because a `workflow_run` apply is queued against the SHA that CI went green on, `main` can move on before that run reaches Azure. The apply job therefore checks that its SHA is still the tip of `main` **before** authenticating, and **re-checks immediately before `terraform apply`** to close the window between the two. A run that has been superseded by a newer commit **skips cleanly** — green, not red — and leaves reconciliation to the newer commit's own run. The recovery `workflow_dispatch` path pins `main` at startup and re-checks the same way; if `main` moved while the run sat waiting for approval, it stops and requires a fresh recovery run rather than applying a trunk state nobody approved.

**What the circuit-breaker protects.** It is not destroy-only. It blocks any plan that would **destroy** a resource _or_ **`forget`** one — the action a `removed { destroy = false }` block produces, which drops a resource out of Terraform management while leaving it alive in Azure, and which every downstream control (secret gate, drift plan) would otherwise report as green. Authorization is an **exact, action-qualified token set** supplied on the recovery path, so approving `delete:<address>` cannot authorize `forget:<address>`, and current and deposed objects sharing one address are enumerated and approved individually. The gate fails closed on any plan shape it cannot classify. The exact token syntax and the operator procedure live in [MG-23 live acceptance & activation](../infrastructure/mg23-live-acceptance.md).

A concrete example: `cosmos_enable_free_tier` (MG-48) sets `free_tier_enabled` on the Cosmos account, an attribute Azure only accepts at account creation, so _any_ change to it — in either environment — plans a **destroy** of `module.cosmos_db.azurerm_cosmosdb_account.main` before recreating it. The automatic `workflow_run` path carries no `authorized_changes` input at all, so it cannot pass this token and the circuit-breaker refuses that apply by design. Clearing it requires the branch-restricted `workflow_dispatch` recovery path with `delete:module.cosmos_db.azurerm_cosmosdb_account.main` in `authorized_changes`, reviewed and approved per the MG-23 procedure linked above.

Every job in both halves gates on the repository variable `vars.DEV_TF_BACKEND_READY == 'true'` and **skips cleanly** (green, not red) when it is unset. Activation is operator-controlled and has prerequisites — see [MG-23 live acceptance & activation](../infrastructure/mg23-live-acceptance.md).

**State locking.** Only the **apply** half touches state at all, so it is the only half that locks. Every `terraform plan` and `terraform apply` inside `infra-apply-dev.yml` passes `-lock-timeout=5m`, so a contending operation **waits** for the Azure blob lease on `meatgeek-v2/dev.tfstate` instead of failing immediately (`init` does not lock), and the apply-vs-apply case is separately serialized by the `infra-apply-dev-development-infra-apply` concurrency group with `cancel-in-progress: false`. The PR half has no lock semantics to discuss because it opens no backend: `terraform init -backend=false` means there is no state to lease, contend for, or corrupt.

**What CI reconciliation does _not_ cover.** Bootstrap (remote state + the OIDC identities), creation of `meatgeek-v2-dev-rg` itself, subscription-scoped configuration, and disaster recovery remain **operator** actions. The dev apply identity is scoped to `meatgeek-v2-dev-rg`, so Terraform can only _adopt_ that resource group — if dev state or the RG is lost, the GitOps loop cannot rebuild it. "CI reconciles dev infrastructure" does not imply a rebuild capability. The final drift plan proves convergence of Terraform-managed **control-plane** resources only; out-of-band role assignments and Cosmos data-plane `sqlRoleAssignments` are invisible to it, and Activity Log alerts are the compensating control.

**Dev applications.** The Functions API is deployed by its own workflow, [below](#dev-app-deploy-and-live-acceptance-mg-36); the web app is not deployed by any workflow.

**Credentials.** **The pull-request path holds no identity at all** — `validate-infrastructure` binds no environment, declares no `id-token: write`, and calls no `azure/login`, so nothing reachable from a PR can authenticate to Azure. Everything that _does_ authenticate runs post-merge or on dispatch.

There are **three** dev identities, plus prod, all authenticating via **per-environment OIDC** rather than the retired long-lived `AZURE_CREDENTIALS` service-principal secret; each job declares `permissions: id-token: write` scoped to itself. Under MG-23 the _environment_ is what separates the privilege levels: `development-infra-apply` federates the infra-apply identity, `development` federates the app-publish identity (used by `app-deploy-dev.yml` to publish the API and to call it in the acceptance run), and `production` federates the prod plan/read identity (which is unchanged by MG-23 and still used by `infra-deploy-prod.yml`). Before MG-23 the dev identities federated the identical `environment:development` subject, so a one-line client-id edit could silently upgrade a low-privilege job to full apply; across environments it no longer can, because the OIDC subject would stop matching and the login would fail closed.

**One sanctioned exception: the acceptance peer shares `development` (HAR-61).** The third dev identity, `meatgeek-v2-dev-acceptance-peer` (`AZURE_ACCEPTANCE_PEER_CLIENT_ID`), is the second caller for the HAR-55 cross-user proof, and it federates the **same** `environment:development` subject as the app-publish identity. So **within `development` the client id a job passes does select the identity**: pass the app-publish client id and you sign in as app-publish, pass the peer's and you sign in as the peer. Both logins succeed; neither fails closed. This is safe only because the peer holds **zero Azure role assignments**: swapping to it can only reduce privilege, bootstrap re-checks that it holds none on every run and dies if it holds any, and `assert_federated_environment_map` permits this one collision and no other. See the [bootstrap runbook section](../infrastructure/bootstrap-runbook.md#dev-acceptance-peer-identity--zero-roles-second-caller-for-har-55-har-61).

No dev identity can authenticate to prod's `environment:production`.

A fourth environment, `development-infra-apply-recovery`, gates the recovery `workflow_dispatch` path with a required reviewer. It is **approval-only and deliberately not federated** — the `recovery_approval` job binds it purely to pick up its protection rules, holds no `id-token` permission, and never calls `azure/login`.

### Dev app deploy and live acceptance (MG-36)

`.github/workflows/app-deploy-dev.yml` deploys every green `main` commit's API to the dev Function App, then proves the deployed system works with the [live acceptance suite](live-acceptance.md). Nobody runs a deploy or a smoke test by hand.

**Trigger.** `workflow_run` of **Apply Dev Infrastructure**, `types: [completed]`, only when that run's `conclusion == 'success'` and `head_branch == 'main'`. The chain is CI/CD Pipeline (push to `main`) → Apply Dev Infrastructure → Deploy Dev App, so a commit's infrastructure, including the Easy Auth caller list the acceptance job relies on, is applied before its API is published and tested. `workflow_dispatch` is allowed for a manual re-run; the job refuses any ref other than `main`.

**Which commit, and when it is skipped.** The job deploys `workflow_run.head_sha` (on dispatch, the dispatched `main` commit) and checks, on both triggers, that the commit has a **successful CI/CD Pipeline run for a push to `main`**. The check is not redundant on the automatic path: an infra-apply run that skipped as superseded reports `main`'s tip as its `head_sha`, and that tip's CI may have failed or still be running. Without a green CI run, an automatic run skips (green, nothing deployed) and a dispatched run fails. The stale-SHA guard from `app-deploy-prod.yml` runs next — the commit must be `main`'s tip — and again right before publish, so a commit `main` has moved past is skipped, not failed. A `concurrency` group (`app-deploy-dev-development`, `cancel-in-progress: false`) serializes dev deploys.

| Job          | Identity / Environment                                                  | What it does                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                              |
| ------------ | ----------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `deploy`     | app-publish identity (`vars.AZURE_APP_DEPLOY_CLIENT_ID`), `development` | `npx nx build api` → `node apps/api/tools/verify-func-package.js dist/apps/api` → `npm install --omit=dev --ignore-scripts` in `dist/apps/api` → read `function_app_name`, `function_app_hostname`, `functions_auth_audience`, `iot_hub_name`, `iot_hub_hostname` and `simulated_device_id` from dev Terraform state (each must be non-empty) (`terraform init` with `environments/backend-dev.hcl`, then `terraform output -raw`) → `func azure functionapp publish <name> --javascript --no-build`, Core Tools pinned to the same version as prod                                                                       |
| `acceptance` | same identity, `development`; runs only if `deploy` published           | builds `simdevice` (`actions/setup-go` from `apps/data-pusher/go.mod`, then `make -C apps/data-pusher build`) → installs the pinned `azure-iot` CLI extension → ensures the simulated device exists (see below) → in the suite step only, fetches and masks the device connection string, mints an app-only token with `az account get-access-token --scope "<functions_auth_audience>/.default"`, masks it, runs `npx nx run api:acceptance` with `ACCEPTANCE_BASE_URL=https://<function_app_hostname>/api` → writes the proof results, `METRIC` lines and the RU-per-route table to the run summary. Timeout 40 minutes |

**Why this publish method.** It is the method proven by hand in MG-21. The bare `nx deploy api` target does not work on Flex Consumption. `--no-build` uploads the package as built, so its runtime dependencies are installed into `dist/apps/api` first. `--javascript` is required because Core Tools reads the legacy `FUNCTIONS_WORKER_RUNTIME` setting, which a Flex app correctly lacks.

**The acceptance caller.** The suite calls the API as the app-publish identity (owner decision: no new identity). Easy Auth accepts it because its client id is in `functions_auth_allowed_client_app_ids` in `apps/infrastructure/environments/dev.tfvars`, next to the Azure CLI public client that delegated, by-hand runs use. The token is app-only, so the cooks the suite writes land in that identity's partition (`<tenant id>:<service principal object id>`), not a user's. The token is minted, masked with `::add-mask::` and used inside one step; it never reaches `$GITHUB_ENV` or a step output.

**The simulated device (HAR-39).** The acceptance job sends real readings through IoT Hub as the standing simulated device `meatgeek-dev-simulated-smoker` (`simulated_device_id` in `dev.tfvars`). Custody model (owner decision): the app-publish identity holds `IoT Hub Registry Contributor` scoped to the dev hub (`simulated_device_registry_contributor` in [`apps/infrastructure/main.tf`](../../apps/infrastructure/main.tf), switched on by HAR-42); the job fetches the device key at run time and masks it, and nothing is stored: no hub shared-access policy, no Key Vault, no repo secret.

- **Go build.** `actions/setup-go` (SHA-pinned, `go-version-file: apps/data-pusher/go.mod`) and `make -C apps/data-pusher build`, which leaves the binary at `apps/data-pusher/dist/simdevice`.
- **CLI extension.** `az extension add --name azure-iot --version 1.0.0`, pinned, after `azure/login`.
- **Device ensure.** Its own step: `az iot hub device-identity show --auth-type login`; on "device not found" (az exit 3, `ResourceNotFoundError`) only, `az iot hub device-identity create` with the same flags (symmetric-key auth). Any other error fails the step, so "not found" is never confused with "not authorised". The step prints `device <id>: exists` or `device <id>: created`; command stdout is discarded because device JSON carries the keys. `--auth-type login` makes `az` use the identity's Entra role rather than hub keys it cannot list, and `--hub-name` is given the hub's hostname (`iot_hub_hostname`), because with a bare name `azure-iot` first looks the hub up through ARM, which a data-plane-only role cannot read.
- **Credential fetch and mask scope.** Inside the "Run the live acceptance suite" step only: `az iot hub device-identity connection-string show … --auth-type login --query connectionString -o tsv` into a shell variable, never echoed. The step fails if it is empty or has no `SharedAccessKey=`; both the full string and the key value are registered with `::add-mask::` before the suite starts. The suite's process gets `SIMDEVICE_CONNECTION_STRING`, `ACCEPTANCE_SIM_DEVICE_ID` and `ACCEPTANCE_SIMDEVICE_BIN` (absolute path of the built binary). None of them reaches `$GITHUB_ENV`, a step output, or another step, the same as `ACCEPTANCE_BEARER_TOKEN`.
- **Metrics.** The summary step copies every log line that starts with `METRIC ` (for example `METRIC roundtrip-ms 2140`) into the run summary, next to the proof lines.

**Credentials.** Both jobs hold `id-token: write`, so every `uses:` in the file is pinned to a full commit SHA (MG-39). Workflow permissions are `contents: read`, `id-token: write` and `actions: read` (for the CI-run lookup). There is no pull-request trigger: `workflow_run` always runs the workflow file from `main`, and both jobs check out a commit that is on `main` and CI-green. Terraform reads dev state over OIDC as the app-publish identity (`ARM_USE_OIDC`), using the Storage Blob Data Reader grant `bootstrap.sh` gives it on `tfstate-dev`; it plans and applies nothing.

**Residual: the race with a newer commit's infra apply.** If an older commit's infra-apply run skips as superseded, this workflow can deploy the newer tip before that tip's own infra apply has finished. The publish is still correct, but an acceptance run that depends on an infrastructure change in that commit can go red. The tip's own infra-apply run triggers a fresh deploy and acceptance run, which is the one that counts.

### Prod

Production deployment is **not** in `ci.yml`. It lives in two standalone workflows so infrastructure and the app can be deployed independently:

| Workflow                | Triggers                                                                                                   | What it deploys                                                                                                                                                                                                                              |
| ----------------------- | ---------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `infra-deploy-prod.yml` | `workflow_dispatch` only (manual / recovery)                                                               | Terraform infrastructure — **plan-only** (`terraform init` binding the prod remote backend + `terraform plan`, **no `apply`**); the prod apply is still the operator's out-of-band step until **MG-25** activates CI-run prod reconciliation |
| `app-deploy-prod.yml`   | `workflow_run` — after the **CI/CD Pipeline** workflow completes (no push trigger, no `workflow_dispatch`) | Functions API only, via `nx deploy api --functionApp=<prod Function App name>`                                                                                                                                                               |

Prod is **API-only** — no workflow in this repo deploys the web frontend, in prod or in dev. That is a statement about **automation**, not about capability: `apps/web/project.json` defines a working `deploy` target, and `nx deploy web --args="--env=<env>"` (an operator-run `az staticwebapp deploy` against a locally built `dist/apps/web`) is how the frontend ships today. See [Azure Deployment](nx-commands.md#azure-deployment).

MG-23 removed the plan-only `deploy-dev` job and the CI **upload** of the web bundle. Nothing in this repo runs `download-artifact`, so that upload had no consumer and `nx deploy web` never depended on it — the removal did not break the deploy path. `nx build web` still runs in CI, so the web app keeps its compile-time signal. Adding a web deploy **workflow** is out of MG-23's scope.

#### App deploy: CI-gated via `workflow_run`

`app-deploy-prod.yml` does **not** trigger on push. It runs on `workflow_run` when the **CI/CD Pipeline** workflow (`ci.yml`) _completes_, and only deploys when **all** of the following hold on the triggering CI run:

- `conclusion == 'success'` — CI was green
- `event == 'push'` — it was a push, not a pull request
- `head_branch == 'main'` — the push targeted `main`
- `vars.PROD_DEPLOY_ENABLED == 'true'` — the operator switch (a **repository variable**, not a secret) is flipped on

This means prod app deploys only ever happen **after green CI on a push to `main`**, and never for a PR or a red build. `PROD_DEPLOY_ENABLED` is the master on/off switch: leave it unset (or anything other than `'true'`) to keep prod deploys dark; set it to `'true'` when you want green pushes to `main` to ship.

**Stale-SHA guard.** The deploy job checks out the exact commit CI ran against (`github.event.workflow_run.head_sha`), but first compares that SHA to the current `main` tip. If `main` has already advanced past the CI'd commit, the job **skips cleanly (green, not a failure)** — it never deploys a commit that is no longer the head of `main`. When several pushes land in quick succession, only the run whose commit is still the tip deploys.

**Retrying a failed deploy.** There is **no `workflow_dispatch`** on the app deploy. To retry, use GitHub's **re-run** on the relevant Actions run (the CI/CD Pipeline run, or the deploy run itself) — there is no manual trigger to invoke by hand.

**Build and package check.** The job builds its own artifact (`corepack enable` → `npm ci` → `nx build api`); there is no artifact sharing between workflows. Before publishing it runs `node apps/api/tools/verify-func-package.js dist/apps/api`, which validates that the build is a well-formed Azure Functions (Node v4) package — `host.json` and `package.json` present and correct at the package root. Azure Functions Core Tools is pinned via `FUNC_CORE_TOOLS_VERSION` (currently `4.12.1`) so the publish toolchain does not drift.

#### Infra deploy: plan-only, manual — pending MG-25

`infra-deploy-prod.yml` is **`workflow_dispatch`-only** and **plan-only** — it binds the per-environment `azurerm` remote backend (`terraform init -reconfigure -backend-config=environments/backend-prod.hcl -backend-config="storage_account_name=$(scripts/state-account-name.sh "$ARM_SUBSCRIPTION_ID")"` — the derived state-account name is injected as an extra `-backend-config` because the `backend-*.hcl` files deliberately omit it; prod's isolated state key `meatgeek-v2/prod.tfstate`) and runs `terraform plan -var-file=environments/prod.tfvars -out=tfplan`, but **does not `apply`**.

This is a **not-yet**, not a never. CI-run reconciliation is the intended steady state for both environments; dev is live under MG-23 and **prod activates under MG-25**. Prod stays manual today because prod state is still greenfield — an unattended apply would create the entire prod stack on its first run — and because prod has no equivalent of dev's least-privilege infra-apply identity yet. Until MG-25, prod infra runs are dispatched by hand, stop at the plan, and the apply is the operator's out-of-band step after reviewing that plan.

**Credentials and environment.** Both prod workflows authenticate via **per-environment OIDC** — `azure/login@v2` with the GitHub-Environment-scoped federated credential (subject `environment:production`), **not** the retired long-lived `AZURE_CREDENTIALS_PROD` service-principal secret. Each declares `permissions: id-token: write` so `azure/login` can mint a short-lived OIDC token, and reads the `AZURE_CLIENT_ID` / `AZURE_TENANT_ID` / `AZURE_SUBSCRIPTION_ID` **`production` Environment variables** (with `ARM_SUBSCRIPTION_ID` sourced from `AZURE_SUBSCRIPTION_ID` for Terraform). These variables only resolve for jobs that declare `environment: production` — in `app-deploy-prod.yml` that is the deploy job; in `infra-deploy-prod.yml` both the `guard` and `deploy-infra` jobs. Both workflows set `concurrency` to not cancel in-progress runs. The infra workflow's `guard` job checks that the three OIDC Environment variables are set and skips cleanly (green) if any is absent. The app workflow has no such guard — it is gated by `PROD_DEPLOY_ENABLED`. There are no long-lived deploy secrets to commit.

### Architecture site (HAR-52)

`.github/workflows/architecture-site.yml` ("Publish Architecture Site") builds the [LikeC4 architecture model](../architecture/likec4/README.md) and publishes it to GitHub Pages at **<https://stevebargelt.github.io/meatgeekv2/>**.

- **Trigger.** `push` to `main` only, with **no** path filter: every merge publishes, so the site always matches `main`. No `pull_request`, `workflow_run` or `workflow_dispatch`. To republish without a new merge, re-run the latest run on `main`.
- **Permissions.** Workflow-level `contents: read`, `pages: write`, `id-token: write`, and nothing else. `id-token: write` is there only because `actions/deploy-pages` needs it to call the Pages deployment API. There is no Azure login and no secret, and the only environment is `github-pages`, which no bootstrap federated credential trusts. Because the workflow holds `id-token: write`, every `uses:` is pinned to a full commit SHA (MG-39).
- **Concurrency.** `group: pages`, `cancel-in-progress: false`, so a deploy already running finishes before the next one starts.
- **`build` job.** `corepack enable` → `npm ci --prefix docs/architecture/likec4` → `npm --prefix docs/architecture/likec4 run check` (a model that fails its checks is never published) → `npx --prefix docs/architecture/likec4 likec4 build docs/architecture/likec4 -o <runner temp>/architecture-site --base /meatgeekv2/ --use-hash-history --title "MeatGeek V2 architecture"` with the `likec4` version pinned in that directory's lockfile → `actions/upload-pages-artifact`.
- **`deploy` job.** `needs: build`, binds the `github-pages` environment, and runs `actions/deploy-pages`; the environment URL is the published site.

**Hash links.** The site is built with `--use-hash-history`. GitHub Pages has no SPA fallback, so a path such as `/meatgeekv2/view/index/` would 404 on reload. Link to views in hash form instead, for example `https://stevebargelt.github.io/meatgeekv2/#/view/index/`; those always resolve.

To preview the site locally, run the same build into any directory and serve it under `/meatgeekv2/`, or use `npm --prefix docs/architecture/likec4 start` for the dev server.

## Branch Protection

`main` is protected. Merges require the following quality jobs to pass:

- `setup`
- `lint-and-test`
- `build-typescript`
- `build-go`
- `validate-infrastructure`
- `security-scan`

`api-cosmos-emulator` (HAR-12) is **not yet** on this list. Add it once it has a run history on `main` that shows it is stable on GitHub-hosted runners.

`validate-infrastructure` **is** a required check, and under MG-23 it carries the whole _Terraform-side_ pre-merge gate: with no PR-time plan, the credentialless sequence (`assert-credentialless.sh` → `fmt -check` → backend-less `init` → `validate` → `terraform test` → `tf-static-checks.sh` → `bootstrap.test.sh` → destroy-guard fixtures → per-module `terraform test` → OTel config validate) is what stands between a bad infrastructure change and an automatic post-merge apply. It is not quite alone: the `api-interfaces` leg of `lint-and-test` is also required, and it is where the workflow-structure specs (the apply workflow's trigger gating and job reachability, the OIDC subject map, the toolchain pins) and the secret-gate fixture regression actually execute — so a change that quietly rewrote the apply workflow's gating would fail there, not here. Because neither job needs a credential, both run unconditionally on every PR, so there is no "absent on most PRs" problem to work around — which is precisely why they can be required at all, where the old PR-only plan job could not.

Deployment and reconciliation are **excluded** from the required checks — `infra-apply-dev.yml` and `app-deploy-prod.yml` are triggered by CI _completing_ on a push to `main`, `infra-deploy-prod.yml` is manual, and `architecture-site.yml` runs only on a push to `main`, so none of them can be a merge gate.

Branch protection on `main` is **load-bearing under MG-23**: a merge to `main` now drives an automatic infrastructure apply holding Contributor and a conditioned Role Based Access Control Administrator on `meatgeek-v2-dev-rg`. Tightening it — `enforce_admins` plus review requirements — is a prerequisite for setting `DEV_TF_BACKEND_READY` to `true`, and is covered in [MG-23 live acceptance & activation](../infrastructure/mg23-live-acceptance.md).

Branch protection is configured on the GitHub repository (Settings → Branches), not in a tracked file. When you add or rename a required job in `ci.yml`, update the required-status-check list to match, or the new job will run without gating merges.

### Agent-delivered changes

Some pull requests are opened by an automated engineer working on a per-issue branch.
Those pull requests go through exactly the same required checks listed above as any other pull request — there is no bypass or reduced gate.
An independent reviewer checks the diff before the work is considered done.
The repository owner performs every merge to `main`; the automated engineer never merges.

## npm and the Lockfile

`package.json` pins the toolchain via `"packageManager": "npm@10.9.8"`, and CI activates it with a `corepack enable` step before `npm ci` in every dependency-installing job (`setup`, `lint-and-test`, `build-typescript`, `security-scan`, `architecture-model`). Corepack reads the `packageManager` field and provisions npm 10.9.8 automatically, so both the runners and local contributors resolve dependencies with the same pinned npm. (`engines.npm` remains `>=10.0.0` as a floor.)

Why npm 10 rather than 11: npm 11 (the default in some local/container environments) omits the nested optional-peer entries (for example `babel-plugin-macros`, `cosmiconfig`, `yaml`) that npm 10 expects. A lockfile written by npm 11 therefore fails `npm ci` on the runners with a sync error. The npm-10 lockfile is a compatible superset, so it works under both.

With the pin in place, no manual workaround is needed. Run `corepack enable` once in your clone (see [Local Setup](local-setup.md)) and any `npm install` that touches dependencies will regenerate `package-lock.json` under npm 10.9.8 automatically.
